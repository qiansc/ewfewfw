# Skills 设计概述

## 文档目的

本文档讨论如何通过 Skills 封装用户故事，让用户和 Agent 能够自然、稳定地完成架构知识管理任务，而无需直接接触 MCP 工具。

## 问题陈述

### 当前挑战

1. **工具调用随机性**：虽然文档清楚，但 Agent 和用户不知道"什么时候该用什么工具"
2. **缺少引导机制**：用户故事描述了理想流程，但没有机制保证实际执行时遵循
3. **稳定性问题**：同样的需求，不同次执行可能调用不同的工具组合
4. **学习成本高**：用户需要理解 MCP 工具体系才能有效使用

### 设计目标

1. **隐藏 MCP 复杂性**：用户通过 Skills 完成任务，不需要知道底层工具
2. **固化最佳实践**：将用户故事中的标准流程封装为 Skills
3. **提高稳定性**：相同场景使用相同的工具编排
4. **降低学习成本**：用户只需记住场景名称

## 设计原则

### 1. Skills 粒度：完整流程

Skills 应该对应完整的用户故事，而非原子操作。

**示例**：
- ✅ `/c4a:feat` - 对应 Feature 管理的完整流程
- ❌ `/c4a:system:create` - 过于原子化，用户需要自己组合

### 2. 路由优先

通过 Skill 名称路由到不同能力，而非让用户选择工具。

**示例**：
```
用户: "我想记录一个新需求"
Agent: 识别意图 → 路由到 /c4a:feat
```

### 3. 禁止直接接触 MCP

Skills 是唯一入口，用户不应该直接调用 MCP 工具。

**例外**：Agent 内部可以调用 MCP 工具，但对用户透明。

### 4. Agent 可通过 Bash 执行 CLI 命令

当 Skill 工作流需要执行同步等操作时，Agent 应通过 Bash 工具执行 `c4a` CLI 命令，而非直接调用 MCP 工具。

**原因**：
- Local 模式：MCP 服务可直接访问本地文件系统进行同步
- Server/Remote 模式：MCP 服务无法访问用户本地 `.context/` 目录，需要 CLI 收集本地文件信息后调用 `c4a_store_plan_sync` 获取同步计划
- `c4a sync` CLI 命令在所有模式下都可用，内部会根据模式选择正确的同步策略

**示例**：
```typescript
// 在 Skill 工作流中执行同步
if (userConfirmedSync) {
  await bash("c4a sync");  // 适用于 Local/Server/Remote 所有模式
}
```

## 能力边界与确认点

为避免过度依赖 LLM 的稳定性，Skills 需要明确能力边界与用户确认点：

1. **意图识别非确定**：自然语言触发仅给出建议，必须等待用户确认后再执行
2. **多步骤流程易丢上下文**：每个关键阶段都要回显当前状态与下一步
3. **语义判断不保证正确**：架构变更、影响分析、ADR 触发仅作为辅助提示
4. **高风险操作必须确认**：
   - 发布/合并/删除/回滚/同步等写操作
   - 跨项目写入与权限敏感操作
   - 任何可能覆盖本地文件的操作

> **原则**：宁可多一次确认，也不自动执行不可逆操作。

## 触发方式

Skills 支持两种触发方式：

| 方式 | 说明 | 示例 |
|------|------|------|
| **显式命令** | 直接调用 Skill 名称 | `/c4a:feat "用户登录"` |
| **自然语言** | Agent 识别意图后建议使用 Skill | "我想开发登录功能" → Agent 建议 `/c4a:feat` |

### 推荐做法

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| 日常使用 | 自然语言 + Agent 建议 | 体验更好，无需记命令 |
| 验收测试 | 显式命令 | 确定性高，可重复验证 |
| 关键操作 | 显式命令 | 避免意图误判 |

### 意图识别机制

当 Agent 通过自然语言识别到意图时，会先告知识别结果并征求确认：

```
用户: "我想优化登录流程"

Agent:
我理解你想进行架构变更。建议使用 `/c4a:feat` 创建一个 Feature，
并在其中记录 ADR。

是否继续？
```

**确认后再执行**，避免意图误判导致的流程错误。
