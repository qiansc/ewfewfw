# C4A 用户故事

> **相关文档**：
> - Skills/Commands 设计：[detailed-design/skills-design.md](./detailed-design/skills-design.md)
> - 核心概念：[concepts.md](./concepts.md)
> - 架构设计：[architecture.md](./architecture.md)

> **注意**：本文档中提到的"知识库"、"DSL"等概念，通常会导出到本地文件系统的 `.context/` 目录下（用于版本控制和人类阅读，也承载项目配置与 feat 工作区）。
> 数据库是权威数据源；`.context/` 中的实体文件更多是**导出/工作区产物**，常规流程不要求人手编辑。必要时（高级/兜底路径）可手工编辑后通过 `c4a sync` 同步并对齐。

## 核心原则

```
人类 ←──自然语言/文档──► Agent ←──内部维护──► DSL 知识库
```

- **人类通过自然语言和文档与 Agent 交互**，不直接接触 DSL
- **DSL 是 Agent 内部的知识结构**，用于精确表达和追溯
- **Agent 负责文档 ↔ DSL 的双向转换**，确保知识一致性

## US-001: 需求迭代全流程（MRD → Code 交付）

### 背景

产品经理主导的标准需求迭代流程，从 MRD 到代码交付。

### 角色

| 角色 | 职责 |
|------|------|
| 产品经理 | 建立业务知识、定义 Story |
| 技术负责人/开发 | 编写技术方案、实现代码 |
| 测试 | 基于验收清单验收功能 |

### 用户故事

#### Story 1: 产品经理建立业务知识

**作为** 产品经理
**我想要** 将 MRD/PRD 文档提供给 Agent，通过对话澄清、确认并创建业务知识
**以便于** 团队和 Agent 都能理解业务背景

**对应 Skill**：`/c4a:feat`（创建 Feature）

**交互方式：**
- 产品经理提供 MRD/PRD 文档
- 与 Agent 自然语言对话，澄清需求
- Agent 生成业务知识文档供确认
- 确认后 Agent 在知识库中维护 Product、Business Process DSL

**验收标准：**
- [ ] MRD/PRD 内容被 Agent 理解并结构化
- [ ] 业务知识文档生成完成
- [ ] Agent 能基于业务知识回答相关问题

---

#### Story 2: 产品经理拆分 Story 并定义需求

**作为** 产品经理
**我想要** 与 Agent 讨论，将 Feature 拆分为多个 Story，并描述每个 Story 的需求
**以便于** 团队可以按 Story 分批迭代交付

**对应 Skill**：`/c4a:specify`

**交互方式：**
- 产品经理用自然语言描述需求
- Agent 生成 PRD 文档供阅读和确认
- 确认后 Agent 在知识库中维护 Functional Spec

**验收标准：**
- [ ] Feature 拆分为可独立交付的 Story
- [ ] 每个 Story 有对应的 PRD 文档
- [ ] Agent 在知识库中维护 Functional Spec（含 Business Process 和 Business SoR）

---

#### Story 3: 研发编写技术方案

**作为** 技术负责人/开发
**我想要** 基于 PRD 与 Agent 讨论技术方案，进行澄清和详细设计
**以便于** 有明确的技术方案可执行

**对应 Skill**：`/c4a:plan`

**交互方式：**
- 研发用自然语言讨论技术方案
- Agent 生成技术方案文档供阅读和确认
- 确认后 Agent 在知识库中维护 Technical Spec

**验收标准：**
- [ ] 技术方案文档覆盖 PRD 中的所有需求点
- [ ] Agent 在知识库中维护 Technical Spec（含 System/Container/Component 和 Contract）
- [ ] 技术方案文档可供团队评审

---

#### Story 4: 研发实现代码

**作为** 开发
**我想要** 基于技术方案文档实现代码
**以便于** 功能可以上线交付

**对应 Skill**：`/c4a:implement`

**交互方式：**
- 开发基于技术方案文档编写代码
- 遇到问题时与 Agent 自然语言讨论
- Agent 基于内部 DSL 知识回答实现细节问题

**验收标准：**
- [ ] 代码实现符合技术方案
- [ ] 单测覆盖关键逻辑
- [ ] Agent 能基于 DSL 知识辅助代码实现

---

#### Story 5: 测试验收功能

**作为** 测试
**我想要** 获取验收清单并据此验收功能
**以便于** 确保交付的功能符合业务和技术要求

**对应 Skill**：`/c4a:analyze`（生成验收清单）、`/c4a:feat --status=published`（发布）

**交互方式：**
- 测试向 Agent 请求生成验收清单
- Agent 基于内部 DSL 生成人类可读的验收清单
- 测试执行验收，结果反馈给 Agent

**验收标准：**
- [ ] 验收清单从 DSL 自动生成
- [ ] 验收结果可追溯到具体需求点
- [ ] Agent 能辅助生成测试用例

## US-002: 研发主导的工具开发（无产品参与）

### 背景

研发自主开发工具或技术改进，没有产品经理参与，输入是混合了调研、交互和技术的方案文档。

### 角色

| 角色 | 职责 |
|------|------|
| 研发 | 提供混合方案文档、澄清需求和技术、实现代码 |

### 用户故事

#### Story 1: 研发提供混合方案文档

**作为** 研发
**我想要** 将调研、交互和技术混合的方案文档提供给 Agent
**以便于** Agent 帮助我梳理和结构化需求

**对应 Skill**：`/c4a:feat`（创建 Feature）

**交互方式：**
- 研发提供混合方案文档
- Agent 分析文档，识别出业务需求和技术方案
- Agent 生成结构化的分析结果供确认

**验收标准：**
- [ ] Agent 能识别文档中的需求点和技术点
- [ ] 生成初步的 Story 拆分建议

---

#### Story 2: Agent 引导澄清并拆分 Story

**作为** 研发
**我想要** Agent 按顺序引导我澄清问题，确定 Story 和技术方案
**以便于** 需求和方案都清晰明确

**对应 Skill**：`/c4a:specify` → `/c4a:plan`

**交互方式：**
- Agent 按优先级依次提出澄清问题
- 研发用自然语言回答
- Agent 逐步完善 Story 列表和技术方案
- 最终生成 PRD 文档和技术方案文档供确认

**验收标准：**
- [ ] 所有关键问题都已澄清
- [ ] Story 拆分合理且可独立交付
- [ ] PRD 文档和技术方案文档生成完成
- [ ] Agent 在知识库中维护 Functional Spec 和 Technical Spec

---

#### Story 3: 研发实现代码

**作为** 研发
**我想要** 基于确认的技术方案实现代码
**以便于** 工具可以上线使用

**对应 Skill**：`/c4a:implement`

**交互方式：**
- 研发基于技术方案文档编写代码
- 遇到问题时与 Agent 讨论
- Agent 基于内部 DSL 知识辅助实现

**验收标准：**
- [ ] 代码实现符合技术方案
- [ ] 单测覆盖关键逻辑

## US-003: 架构变更与 ADR 创建

### 背景

研发在方案设计过程中发现会造成架构变更，需要创建 ADR 记录决策。

### 角色

| 角色 | 职责 |
|------|------|
| 研发 | 设计方案、评估架构影响、决策 |

### 用户故事

#### Story 1: Agent 识别架构变更

**作为** 研发
**我想要** 在设计技术方案时，Agent 能识别出架构变更并提醒我
**以便于** 我能及时评估影响并记录决策

**对应 Skill**：`/c4a:plan`（自动检测架构变更）

**交互方式：**
- 研发与 Agent 讨论技术方案
- Agent 分析方案对现有架构的影响
- Agent 识别到架构变更，建议创建 ADR

**验收标准：**
- [ ] Agent 能识别影响现有 System/Container/Component 的变更
- [ ] Agent 主动建议创建 ADR

---

#### Story 2: 创建 ADR 评估影响

**作为** 研发
**我想要** 与 Agent 一起创建 ADR，评估影响面和决策点
**以便于** 架构变更有据可查

**对应 Skill**：`/c4a:feat`（ADR 场景）

**交互方式：**
- Agent 引导研发填写 ADR 的各项内容（背景、选项、决策、影响）
- Agent 基于内部 DSL 分析影响面（哪些 Container/Component 受影响）
- Agent 生成 ADR 文档供评审
- 确认后 Agent 在知识库中维护 ADR DSL

**验收标准：**
- [ ] ADR 包含完整的背景、选项、决策、影响
- [ ] 影响面分析准确
- [ ] ADR 文档可供团队评审

---

#### Story 3: 技术方案与 ADR 关联

**作为** 研发
**我想要** 技术方案与 ADR 关联，方案产出的同时也记录架构变更
**以便于** 知识可追溯

**对应 Skill**：`/c4a:plan`（自动关联 ADR）

**交互方式：**
- Agent 在生成技术方案文档时，自动关联相关 ADR
- 技术方案文档中引用 ADR 的决策点

**验收标准：**
- [ ] 技术方案文档中有 ADR 引用
- [ ] Agent 内部 Technical Spec 与 ADR 关联

---

## US-004: 契约补充与完善

### 背景

研发在阅读技术方案时，发现缺失 API 接口设计，或 Agent 询问补充契约细节。

### 角色

| 角色 | 职责 |
|------|------|
| 研发 | 补充契约细节、提供 API 设计 |

### 用户故事

#### Story 1: Agent 询问契约细节

**作为** 研发
**我想要** Agent 在发现契约不完整时主动询问我
**以便于** 技术方案更加完整

**对应 Skill**：`/c4a:plan`（契约补充）

**交互方式：**
- Agent 分析技术方案，发现契约缺失或不完整
- Agent 向研发提出具体问题（如：这个接口的入参是什么？错误码有哪些？）
- 研发用自然语言回答
- Agent 更新技术方案文档和内部 Contract DSL

**验收标准：**
- [ ] Agent 能识别契约的缺失和不完整
- [ ] 问题具体且有针对性

---

#### Story 2: 研发主动提供 API 设计

**作为** 研发
**我想要** 主动提供 API 接口设计，Agent 采纳并记录
**以便于** 契约完整且可追溯

**对应 Skill**：`/c4a:plan`（契约补充）

**交互方式：**
- 研发用自然语言或代码片段描述 API 设计
- Agent 解析并生成标准化的契约文档（OpenAPI/AsyncAPI）
- Agent 更新技术方案文档，内部索引 Contract DSL

**验收标准：**
- [ ] API 设计被正确解析和记录
- [ ] 契约文档符合标准格式
- [ ] 技术方案文档自动更新

## US-005: 业务知识整理与发布

### 背景

产品输入大量 MRD/PRD，需要系统性整理业务视角知识，并走提案、批准、发布流程。

### 角色

| 角色 | 职责 |
|------|------|
| 产品经理 | 提供文档、澄清业务、审批发布 |

### 用户故事

#### Story 1: 产品提供文档，Agent 建议创建 Feature

**作为** 产品经理
**我想要** 提供一批 MRD/PRD 文档给 Agent，Agent 建议创建一个专门的 Feature 来整理业务知识
**以便于** 业务知识能系统性地建立和管理

**对应 Skill**：`/c4a:know:learn` 或 `/c4a:feat`（纯知识场景）

**交互方式：**
- 产品经理提供多份 MRD/PRD 文档
- Agent 分析文档，识别需要整理的业务知识范围
- Agent 主动建议：创建一个 Feature 用于业务知识整理
- 产品经理确认创建 Feature

**验收标准：**
- [ ] Agent 能分析多份文档并识别知识范围
- [ ] Agent 主动建议创建 Feature
- [ ] Feature 创建成功

---

#### Story 2: 拆分 Story 逐步整理业务知识

**作为** 产品经理
**我想要** 将业务知识整理拆分为多个 Story，逐步澄清和完善
**以便于** 知识整理有序进行

**对应 Skill**：`/c4a:specify` → `/c4a:plan`

**交互方式：**
- Agent 建议 Story 拆分（按 Product、按 Process 等维度）
- 产品经理与 Agent 逐个 Story 澄清业务知识
- Agent 生成业务知识文档供确认
- 确认后 Agent 在知识库中维护 Product、Business Process、Business SoR DSL

**验收标准：**
- [ ] Story 拆分合理
- [ ] 每个 Story 完成后有对应的业务知识文档
- [ ] Agent 内部 DSL 完整

---

#### Story 3: 提案、批准、发布业务知识

**作为** 产品经理
**我想要** 将整理好的业务知识走提案、批准、发布流程
**以便于** 业务知识成为团队的权威知识源

**对应 Skill**：`/c4a:feat --status=approved` → `/c4a:feat --status=published`

**交互方式：**
- Agent 生成提案文档（Draft）
- 产品经理发起评审，相关人员批准（Approved）
- 批准后发布（Published）
- Agent 更新内部 DSL 状态

**验收标准：**
- [ ] 提案文档完整
- [ ] 走完 Draft → Approved → Published 流程
- [ ] 发布后的知识可被团队和 Agent 查询使用

## US-006: 存量知识整理与发布

### 背景

研发输入存量技术方案文档（可能过时）、少量业务文档和代码仓库，需要为指定模块建立完整的业务视角和技术视角知识。

### 角色

| 角色 | 职责 |
|------|------|
| 研发 | 提供文档和代码、澄清知识、审批发布 |

### 用户故事

#### Story 1: 研发提供存量资料，Agent 建议创建 Feature

**作为** 研发
**我想要** 提供存量技术方案、业务文档和代码仓库给 Agent，Agent 建议创建一个 Feature 来整理知识
**以便于** 存量知识能系统性地建立和管理

**对应 Skill**：`/c4a:know:learn` 或 `/c4a:feat`（纯知识场景）

**交互方式：**
- 研发提供技术方案文档、业务文档、代码仓库路径
- Agent 分析资料，识别需要整理的模块和知识范围
- Agent 主动建议：创建一个 Feature 用于存量知识整理
- 研发确认创建 Feature

**验收标准：**
- [ ] Agent 能分析多种类型的资料
- [ ] Agent 识别出过时内容并标记
- [ ] Agent 主动建议创建 Feature
- [ ] Feature 创建成功

---

#### Story 2: 按模块拆分 Story，逐步建立知识

**作为** 研发
**我想要** 按指定模块拆分 Story，逐步建立业务视角和技术视角知识
**以便于** 知识整理有序且可追溯

**对应 Skill**：`/c4a:specify` → `/c4a:plan`

**交互方式：**
- Agent 建议按模块拆分 Story
- 每个 Story 聚焦一个模块，依次整理：
  1. 业务视角知识（Product、Business Process、Business SoR）
  2. 技术视角知识（System/Container/Component、Technical SoR、Contract）
- 研发与 Agent 逐个 Story 澄清，确认文档
- Agent 在知识库中维护完整的双视角 DSL

**验收标准：**
- [ ] Story 按模块拆分
- [ ] 每个模块有完整的业务视角和技术视角知识
- [ ] 代码与技术知识关联（code_path）

---

#### Story 3: 提案、批准、发布存量知识

**作为** 研发
**我想要** 将整理好的存量知识走提案、批准、发布流程
**以便于** 存量知识成为团队的权威知识源

**对应 Skill**：`/c4a:feat --status=approved` → `/c4a:feat --status=published`

**交互方式：**
- Agent 生成提案文档（Draft），标注与现有知识的差异
- 研发发起评审，相关人员批准（Approved）
- 批准后发布（Published）
- Agent 更新内部 DSL 状态，替换或归档旧知识

**验收标准：**
- [ ] 提案文档完整，差异明确
- [ ] 走完 Draft → Approved → Published 流程
- [ ] 发布后的知识可被团队和 Agent 查询使用
- [ ] 过时知识被正确归档

## 附录: feat 冲突场景

### 场景 1: feat 合并时的实体冲突

**角色**: 架构师
**场景**: feat 发布时，主分支的实体已被其他人修改

**用户体验**:
1. 架构师创建 feat-a001，修改 payment-service
2. 另一个开发者在主分支直接修改了 payment-service
3. feat-a001 准备发布时，Agent 检测到冲突
4. Agent 展示冲突详情：
   - 主分支版本：1.5
   - feat 版本：2.0
   - 冲突字段：version, description
5. Agent 分析冲突，提供决策建议（保留哪个版本或合并）
6. 架构师确认决策后，Agent 继续合并剩余实体

**冲突类型**:
- **内容冲突**: 主分支和 feat 都修改了同一实体
- **删除冲突**: 主分支删除了实体，feat 修改了实体
- **类型冲突**: 主分支和 feat 修改了实体的 type/kind

---

### 场景 2: feat 内 ADR 的状态流转

**角色**: 架构师
**场景**: 在 feat 内创建 ADR，随 feat 一起发布

**用户体验**:
1. 架构师创建 feat-a002: 引入消息队列
2. 在 feat 内创建 ADR，记录引入 RabbitMQ 的决策
