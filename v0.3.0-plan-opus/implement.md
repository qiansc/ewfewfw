# v0.3.0 C4A 实现指南

> 本文档是 AI Agent 执行 v0.3.0 实现任务的操作规范

---

## 核心原则

1. **按需加载** - 只加载当前任务需要的上下文，避免一次性加载过多文件
2. **连续执行** - 任务逐个执行，完成后立即继续下一个，无需每次暂停
3. **即时标记** - 每完成一个小任务，**立即**更新详细计划文件中的"已读"和"已实现"状态
4. **变更隔离** - 发现设计问题不直接改源文档，记录到 change 目录
5. **批量验证** - 连续执行 3-10 个任务后暂停，批量验证这批任务
6. **设计文档为准** - 实现必须与设计文档完全一致，不能遗漏任何类型、字段或功能
7. **上下文保护** - 严格控制上下文使用，避免溢出导致会话中断

**重要：计划文件可以修改**
- `v0.3.0-plan-opus/` 目录下的计划文件（如 `01-core-concepts.md`）**可以且必须修改**，用于记录进度
- 只有 `v0.3.0/` 目录下的设计文档不能直接修改

## 执行流程

### 1. 会话开始时

```
1. 加载 summary.md 了解整体进度
2. 确定当前要执行的 Part 和起始任务编号
3. 加载对应的详细计划文件 (如 01-core-concepts.md)
4. 【重要】只规划下一个要执行的任务，不提前规划多个任务
```

### 2. 连续执行任务 - 批量验证模式

```
对于每个任务 (x.x)：
1. 阅读任务引用的设计文档章节（仅加载当前任务需要的章节）
2. 在详细计划文件中勾选 "已读" [x]
3. 按设计文档实现功能（仅实现当前任务）
4. 遇到设计问题 → 记录到 change/ 目录
5. 实现完成后，在详细计划文件中勾选 "已实现" [x]
6. 【判断】是否到达验证断点？
   - 否 → 立即继续下一个任务
   - 是 → 进入批量验证流程
```

### 2.5 验证断点判断规则

**断点触发条件（满足任一即触发）：**

| 条件 | 说明 |
|------|------|
| 任务数 ≥ 10 | 强制断点，必须验证 |
| 任务数 ≥ 3 且到达逻辑边界 | 如：完成一个完整功能模块、一组相关类型定义 |
| 任务数 ≥ 3 且 tokens 消耗较大 | 产生了大量代码变更，需要及时验证 |
| 任务数 ≥ 3 且下一任务关联性低 | 当前任务组相对独立，适合先验证 |

**断点判断示例：**
```
任务 3.1-3.3: 定义 Entity 基础类型 → 关联性高，继续
任务 3.4-3.5: 定义 Entity 扩展类型 → 类型定义完成，触发断点验证

任务 4.1-4.6: 实现 CRUD 函数 → 功能完整，触发断点验证

任务 5.1-5.10: 大量小任务 → 达到最大数量，强制断点验证
```

### 2.6 批量验证流程（断点时执行）

**到达验证断点后，必须执行以下流程：**

```
1. 统计本批次完成的任务列表
2. 生成验收清单 → checklist/{Part}-{范围}.md
3. 执行自动化验证（typecheck/test/build）
4. 【关键】逐行逐章节对照设计文档验证（见下方详细规则）
5. 记录验收结果
6. 【阻断】验收不通过 → 修复后重新验收
7. 【继续】验收通过 → 继续下一批任务
```

### 2.7 任务级验证规则（每个任务完成时快速检查）

**每个任务完成后，快速检查以下内容（不暂停，发现问题立即修复）：**

#### 类型定义任务
```
□ 设计文档中定义的所有类型是否都已创建？
□ 每个类型的所有字段是否与设计文档一致？
□ 类型文件是否已在 index.ts 中导出？
□ 运行 pnpm typecheck 是否通过？
```

#### JSON Schema 任务
```
□ 设计文档中定义的所有实体是否都有对应的 Schema 文件？
□ Schema 的 $id 是否正确设置？
□ Schema 是否已在 ajvInstance.ts 中注册？
□ validator/index.ts 的 DSLType 是否包含新类型？
□ utils/schema.ts 的 SCHEMA_MAP 是否包含新类型？
```

#### 工具函数任务
```
□ 设计文档中定义的所有函数是否都已实现？
□ 函数签名是否与设计文档一致？
□ 是否有对应的单元测试？
□ 运行 pnpm test 是否通过？
```

#### MCP 工具任务
```
□ 工具名称是否与设计文档一致？
□ 输入参数是否完整？
□ 返回格式是否符合规范？
□ 错误码是否正确使用？
```

**验证失败处理：**
- 发现遗漏 → 立即补充实现
- 发现设计问题 → 记录到 change/ 目录
- 不确定是否完整 → 重新阅读设计文档对照检查

### 2.8 最终验证（提交前必须执行）

**基于设计文档逐行 Review 未提交变更：**

```bash
# 1. 查看所有未提交的变更
git diff --name-only

# 2. 对每个变更文件，对照设计文档逐行检查
```

**Review 检查项：**
```
□ 设计文档中定义的每个类型/字段/函数是否都已实现？
□ 实现的命名是否与设计文档完全一致？
□ 实现的参数/返回值是否与设计文档一致？
□ 是否有设计文档中定义但未实现的内容？
□ 是否有实现了但设计文档中未定义的内容？
```

**Review 流程：**
1. 打开设计文档对应章节
2. 逐行阅读设计文档中的定义
3. 在代码中查找对应实现
4. 确认实现与设计完全一致
5. 发现遗漏立即补充

### 3. 会话结束时

```
1. 确保所有已完成任务的状态都已更新
2. 统计本次会话完成的任务数量
3. 如果有未验证的任务批次 → 执行批量验证（见 §2.6）
4. 更新 summary.md 中对应 Part 的完成状态
5. 验收报告输出到 v0.3.0-plan-opus/checklist/ 目录下
6. 向用户报告本次会话完成情况和下一步建议
```

## 验收清单

### 核心原则：逐章节严格验收

**每个 Part 必须逐章节验收，验收通过后才能进入下一个 Part。**

验收粒度：
- **最小粒度**：单个任务 (x.x)
- **标准粒度**：任务组 (x.1-x.5)
- **最大粒度**：整个 Part

### 验收阻断规则

**以下情况必须阻断，不能进入下一个任务组：**

1. **类型不完整** - 设计文档中定义的类型未全部实现
2. **字段缺失** - 类型中的字段与设计文档不一致
3. **导出遗漏** - 新增类型未在 index.ts 中导出
4. **Schema 未注册** - 新增 Schema 未在 ajvInstance.ts 中注册
5. **测试失败** - 单元测试未通过
6. **构建失败** - pnpm build 失败

### 验收检查命令

```bash
# 快速验收脚本（每个任务组完成后执行）
pnpm typecheck && pnpm test && pnpm build

# 如果上述命令全部通过，再进行手工对照验收
```

### Part 完成标准

一个 Part 完成的标准：

1. **所有任务组验收通过** - 每个任务组都有对应的验收清单且状态为"通过"
2. **summary.md 已更新** - Part 的完成状态已勾选
3. **无遗留问题** - 或遗留问题已记录到 change/ 目录

---

## 注意事项

1. **上下文控制** - 文件很多，严格按需加载，避免上下文溢出
2. **即时更新** - 每完成一个 x.x 任务，立即更新详细计划文件的勾选状态
3. **连续执行** - 任务完成后立即继续下一个，无需等待用户确认
4. **智能断点** - 根据任务关联性和 tokens 消耗量决定验证断点（3-10 个任务）
5. **批量验证** - 到达断点时暂停，逐行逐章节对照设计文档验证
6. **变更追溯** - 设计问题记录到 `change/` 目录，便于后续回顾
7. **验收驱动** - 先明确验收标准，再开始实现
8. **避免溢出** - 严格控制每次加载的文件数量和代码量
