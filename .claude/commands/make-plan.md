# /make-plan - 根据 PRD 生成执行计划

根据 PRD 文档、架构现状、代码情况，生成符合规范的执行计划（Plan）。

---

## ⚠️ Agent 职责边界（必须遵守）

**本 Agent 只完成 `/make-plan` 的工作，不做其他事情：**

- ✅ 生成执行计划（Plan）
- ❌ 不执行 `/review-plan`（审查一致性）
- ❌ 不执行 `/fix-plan`（修复问题）
- ❌ 不执行实现任务
- ❌ 不推荐"下一步应该执行 XXX"

**完成 Plan 生成后直接结束，不要建议用户继续执行其他指令。**

## 输入要求

### 必须加载到上下文（⚠️ 强制）

| 输入 | 必需 | 说明 | 上下文要求 |
|------|------|------|-----------|
| **PRD 文档** | ✅ | 产品需求文档，定义 What | **必须完整加载** |
| **代码地图** | ✅ | 代码库结构统计或模块清单 | **必须完整加载** |
| **核心架构文档** | ✅ | 与 PRD 最相关的架构文档 | **必须完整加载** |

### 可选阅读（按需加载）

| 输入 | 说明 |
|------|------|
| 其他架构文档 | 相关但非核心的架构描述 |
| 背景文档 | ADR、技术调研、会议纪要等 |
| 历史 Plan | 参考格式和风格 |

## 输入文档

### 必须加载（执行前必读）

| 文档 | 路径 | 说明 |
|------|------|------|
| PRD | `path/to/prd.md` | 产品需求文档 |
| 代码地图 | `path/to/code-map.yaml` | 代码库结构 |
| 核心架构 | `path/to/architecture.md` | 架构设计文档 |

### 可选阅读

| 文档 | 路径 | 说明 |
|------|------|------|
| ADR-001 | `path/to/adr-001.md` | 相关架构决策 |
| 技术调研 | `path/to/research.md` | 背景调研 |
| ... | ... | ... |

---

## Phase N: [阶段名称]
...
```

### 文档定位

**Plan 是执行计划，不是详细设计**

| 属性 | Plan 应该是 | Plan 不应该是 |
|------|------------|--------------|
| 抽象层级 | How（怎么做） | What（做什么）← PRD |
| 内容形式 | 任务列表 + 验收标准 | 代码实现 + Schema 定义 |
| 代码量 | ≤10 行/块（仅标注修改点） | 完整实现代码 |
| 契约定义 | 引用 PRD 章节 | 重复定义 Schema |

### 任务结构

```markdown
### Task N.M: [任务名称]
- [ ] **PRD 对应**: [PRD 章节/行号]
- **修改文件**:
  - `path/to/file.ts`: [简要说明]
- **实现要点**:
  - [要点 1]
  - [要点 2]
- **验收标准**:
  - [ ] [compile] TypeScript 编译通过
  - [ ] [test] 相关单元测试通过
  - [ ] [inspect] 字段定义符合 PRD 规范
```

#### 验收标准编写规范（必须遵守）

**每条验收标准必须标注验证类型**，帮助执行 Agent 明确如何验证：

| 验证类型 | 标记 | 适用场景 | 示例 |
|---------|------|---------|------|
| `[test]` | 需要运行测试 | 功能正确性、边界条件 | `[test] CRUD 操作通过单元测试` |
| `[compile]` | 需要编译检查 | 类型正确性、接口兼容 | `[compile] TypeScript 编译无错误` |
| `[inspect]` | 需要代码检查 | 字段存在、代码结构 | `[inspect] 新字段已添加到类型定义` |
| `[run]` | 需要运行命令 | 行为验证、输出检查 | `[run] 迁移脚本执行后数据完整` |

**规则**：
- 每个 Task 至少有 1 条验收标准
- 每条验收标准必须以 `[test]`/`[compile]`/`[inspect]`/`[run]` 开头
- 验收标准必须是可验证的具体条件，不能是模糊描述
- 避免写 `实现正确`、`功能完成` 这种无法验证的标准

## 生成流程

### 1. 加载必需文档

**在开始生成前，必须确认以下文档已加载到上下文：**

```
✅ PRD 文档已加载
✅ 代码地图已加载
✅ 核心架构文档已加载
```

如果缺少必需文档，**停止生成并提示用户提供**。

### 2. 分析 PRD 提取关键契约

从 PRD 中提取：
- **数据模型变更**：新增/修改/删除的字段、类型
- **API 契约**：新增/修改的接口、输入输出 Schema
- **行为规则**：业务逻辑、约束条件、错误处理
- **迁移要求**：数据迁移、兼容性处理

输出：契约清单（带 PRD 行号）

### 3. 分析架构现状

**优先使用架构文档**，包含：
- 模块划分和职责
- 依赖关系
- 技术栈

**结合代码地图**，包含：
- 目录结构
- 关键文件清单
- 模块依赖

### 4. 映射契约到任务

将每个 PRD 契约映射到具体任务：

```
PRD 契约 → 影响的模块 → 修改的文件 → 任务描述
```

**映射原则**：
- 一个契约可能对应多个任务（跨模块）
- 多个契约可能合并为一个任务（同模块）
- 每个任务必须有明确的验收标准

### 5. 组织 Phase 和依赖

**Phase 划分原则**：
- 按模块/层级划分（Core → Storage → MCP → CLI）
- 按依赖顺序排列（被依赖的先做）
- 每个 Phase 有独立的验证点

**依赖关系原则**：
- 显式标注任务依赖
- 避免循环依赖
- 识别关键路径

### 6. 识别风险

检查以下风险类型：
- **技术风险**：新技术、复杂算法
- **依赖风险**：外部依赖、版本兼容
- **数据风险**：迁移、一致性
- **时间风险**：关键路径、并行度

## 任务编写规范

### ✅ 正确的任务描述

```markdown
### Task 2.3: 实现 SqliteAdapter
- [ ] **PRD 对应**: §2.4 SQLite 实现要点
- **修改文件**:
  - `packages/storage/src/adapters/sqlite/sqliteAdapter.ts`: 重写适配器
- **实现要点**:
  - 通过 JOIN `entity_versions` 表查询版本
  - 实现 `splitEntity` 事务操作（Copy-On-Write）
  - 实现乐观锁（`updated_at` 检查）
- **验收标准**:
  - [ ] [test] CRUD 操作通过单元测试
  - [ ] [test] Copy-On-Write 分裂正确
  - [ ] [run] 乐观锁冲突返回错误码 C4A-DATA-003
  - [ ] [compile] TypeScript 编译无错误
```

### ❌ 错误的任务描述

```markdown
### Task 2.3: 实现 SqliteAdapter
- **代码实现**:
  ```typescript
  class SqliteAdapter implements IStorageAdapter {
    async save(entity: Entity): Promise<Entity> {
      // 50 行实现代码...
    }
  }
  ```
```

**问题**：包含大量实现代码、没有验收标准

## 特殊场景处理

### 场景 1：PRD 定义了新 API

**Plan 任务**：
```markdown
### Task 3.7: 实现 c4a_store_add_version
- [ ] **PRD 对应**: §3.2.1 addVersion 契约
- **修改文件**:
  - `packages/mcp-store/src/tools/version.ts`: 新增工具
- **实现要点**:
  - 调用 `IStorageAdapter.addVersion()`
  - 检查 0.0.0 保护（返回 C4A-VERSION-005）
- **验收标准**:
  - [ ] [test] 输入/输出符合 PRD Schema
  - [ ] [run] 0.0.0 保护生效，返回 C4A-VERSION-005
  - [ ] [compile] TypeScript 编译无错误
```

### 场景 2：数据迁移

**Plan 任务**：
```markdown
### Task 2.6: 数据迁移（SQLite）
- [ ] **PRD 对应**: §4.1 数据迁移方案
- **迁移步骤**:
  1. 备份数据库
  2. 删除 `requirement_id` 字段
  3. 填充新字段（uuid, root_id, versions）
  4. 验证数据完整性
- **验收标准**:
  - [ ] [run] 迁移前后记录数一致
  - [ ] [run] 所有记录有 uuid
  - [ ] [test] 迁移脚本单元测试通过
```

### 场景 3：跨模块变更

**Plan 任务**（拆分到多个 Phase）：
```markdown
## Phase 1: Core
### Task 1.4: 引入 versions 字段
- **修改文件**: `packages/core/src/types/`

## Phase 2: Storage
### Task 2.2: SQLite Schema 迁移
- **依赖**: Task 1.4

## Phase 3: MCP
### Task 3.1: c4a_store_save 适配
- **依赖**: Task 2.2
```

## Plan 结尾：Agent 拆分与执行策略

**Plan 文档最后必须包含 Agent 拆分建议**，帮助后续执行时合理分配工作。

### 输出格式

```markdown
---

## Agent 拆分与执行策略

### Agent 分配

| Agent | 负责任务 | 依赖 | 预估复杂度 |
|-------|---------|------|-----------|
| Agent 1 | Phase 1 (Task 1.1 ~ 1.8) | 无 | 中 |
| Agent 2 | Phase 2 (Task 2.1 ~ 2.6) | Agent 1 | 高 |
| Agent 3 | Phase 3 (Task 3.1 ~ 3.7) | Agent 2 | 高 |
| Agent 4 | Phase 5 (Task 5.1 ~ 5.6) | Agent 1 | 中 |
| Agent 5 | Phase 6 (Task 6.1 ~ 6.4) | Agent 2 | 低 |

### 执行策略

**串行执行**（有依赖关系）：
```
Agent 1 → Agent 2 → Agent 3
Agent 1 → Agent 4
Agent 2 → Agent 5
```

**可并行执行**（无依赖关系）：
```
批次 1: Agent 1
批次 2: Agent 2 + Agent 4（并行）
批次 3: Agent 3 + Agent 5（并行）
```

### 执行图

```
        ┌─► Agent 2 ─► Agent 3
Agent 1 ┤
        └─► Agent 4
              │
        Agent 2 ─► Agent 5
```

### 注意事项

- 每个 Agent 只完成自己负责的任务，不越界
- Agent 完成后不推荐下一步，由调度者决定
- 并行 Agent 之间不要有隐式依赖

### Agent 收尾：质量门禁（必须遵守）

**凡涉及代码变更的 Agent，结束前必须通过以下三项检查（缺一不可）：**

```bash
# 1. 单元测试 — 按变更模块逐一运行
bun run --filter @c4a/<package> test   # 对每个涉及变更的包执行

# 2. 类型检查 — 全量运行，确保跨包类型一致
bun run typecheck

# 3. Lint 检查 — 全量运行
bun run lint
```

**规则**：
- 三项检查全部通过后才能勾选任务并结束 Agent
- 测试必须按**变更模块粒度**运行（如 `bun run --filter @c4a/storage test`），不能仅运行全量 `bun run test` 然后跳过报错的其他包
- typecheck 和 lint 运行全量命令；若失败项属于本 Agent 修改范围则必须修复，否则记录为「非本 Agent 问题」
- **禁止跳过任何一项**——没有 lint 就不算完成，没有 typecheck 也不算完成

**Plan 中每个有代码变更的 Agent，验收标准必须包含以下三条（模板）：**

```markdown
- **验收标准**:
  - [ ] [test] 涉及变更的包测试全部通过（列出具体包名）
  - [ ] [compile] `bun run typecheck` 无错误
  - [ ] [run] `bun run lint` 无错误
  - [ ] ...（其他业务验收标准）
```

### 最后 Agent 收尾：知识更新

最后一个 Agent 完成后，需要询问用户是否更新知识文档：

| 参数 | 说明 | 示例 |
|------|------|------|
| 旧知识目录 | 当前版本的知识文档位置 | `.tmp/0.3.0-final` |
| 新知识目录 | 新版本知识文档的目标位置 | `.tmp/` |

**执行流程**：

1. **询问用户**：是否需要更新知识文档？
2. **复制目录**：`{旧知识目录}` → `{新知识目录}/{版本号}-final`
3. **扫描更新**：遍历新目录中的每个文件，根据本次 PRD 变更更新内容
4. **更新代码地图**：对比未提交的 commit，确保代码地图与当前实现一致

**示例**：
```
用户输入：
- 旧知识目录: .tmp/0.3.0-final
- 新知识目录: .tmp/

执行结果：
1. 复制 .tmp/0.3.0-final → .tmp/0.3.1-final
2. 更新 .tmp/0.3.1-final/architecture.md（反映数据模型变更）
3. 更新 .tmp/0.3.1-final/map.yaml（与当前代码一致）
4. 更新其他受影响的文档
```
```

### 拆分原则

1. **按 Phase 拆分**：一个 Phase 通常对应一个 Agent
2. **按依赖拆分**：有依赖的任务放同一个 Agent，或明确串行
3. **按复杂度拆分**：复杂任务单独一个 Agent，简单任务可合并
4. **避免过细拆分**：Agent 数量建议 3-7 个，太多增加协调成本

### 依赖分析方法

1. 构建任务依赖图
2. 识别关键路径（最长依赖链）
3. 找出可并行的独立子图
4. 按子图分配 Agent
